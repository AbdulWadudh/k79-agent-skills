## Added

### Adopt caveman and ponytail as opt-in efficiency skills ([`4d1a4e3`](https://github.com/AbdulWadudh/k79-agent-skills/commit/4d1a4e3a3a03ab17ddc84eef204beb7e1bb603c6))

**Scope:** skills/k79-conductor, skills/k79-evidence-and-simplicity, README.md, specs/external-skill-adoption.spec.md

#### Why

The suite carried no rule for token cost. Two third-party skills address it: `caveman` shortens chat prose, `ponytail` shortens the diff. Bundling either would take on their licences and maintenance, and installing either silently would change a user's global skill directory without consent. The suite needed to cooperate with them, ask before touching anything, and make sure neither skill can quietly weaken a k79 rule.

#### What

- `k79-conductor` gains **one Phase 2 bullet**: follow an installed `caveman` or `ponytail`, and keep every k79 rule on top. No detection loop, no install offer, no setup text in the task path.
- `k79-evidence-and-simplicity` names `ponytail`'s ladder as the tie-breaker for YAGNI, bounded by the spec gate, the 250-line cap, the 1:2 test ratio, security, and `@quirk:` shields.
- `K79.reminder.md` and `AGENTS.router.md` each gain one line so the rule survives into any project's `AGENTS.md`; the reminder is now thirteen lines.
- `README.md` holds the whole of setup: a section documenting both skills with upstream links and install commands, and bootstrap step 6, which asks once and runs nothing without a yes. Installation lives nowhere else.
- `specs/external-skill-adoption.spec.md` records the precedence table, the one-time-only setup boundary, and the non-goals, including the rejection of RTK command rewriting.

Neither skill is vendored, added to `skills/`, or recorded in `skills-lock.json`.

#### Verification

- `node scripts/validate-skills.mjs` — frontmatter, name/version match, and k79 reference resolution pass.
- `node scripts/sync-agents.mjs --check` — the marked block in `AGENTS.md` matches the router template.
- `node scripts/release-notes.mjs --check` — the entry schema and append-only history pass.
- Manual read-through against the nine acceptance criteria in the spec, including the conflict cases (test ratio, `@quirk:` shields, approval questions, persisted artifacts).

#### Notes

RTK was evaluated and rejected: an independent paired A/B benchmark measured it at +7.6% tokens, and its docs confirm the gain depends on a rewrite hook that rules-file agents do not have. Ponytail and caveman were measured at −10.3% cost and −8.5% tokens respectively, well below their advertised numbers. The suite treats both as trims, not transformations.

`sync-agents.mjs` manages only the marked router block. The reminder at the top of `AGENTS.md` is a bootstrap-time copy of `K79.reminder.md`, so this entry updates both by hand. Making the check verify the reminder copy is a separate change.

## Changed

### Replace spec checkboxes with six verification status markers ([`6ec183d`](https://github.com/AbdulWadudh/k79-agent-skills/commit/6ec183de2263f77805b6afb334326033738b1c5f))

**Scope:** skills/k79-spec-driven, skills/k79-conductor, skills/k79-verification-testing, specs/spec-status-markers.spec.md

#### Why

`- [ ]` and `- [x]` record one bit: touched or not. That bit lies in the most common case. An agent that reads the wording it just wrote marks a criterion complete, and the spec then claims verification that never ran. Instruction-file rules have no executable check at all, so they could never earn an honest `[x]`.

The suite needed a status that can say "the rule exists but nothing can test it" — otherwise every prose rule is either falsely complete or permanently open.

#### What

- `k79-spec-driven` §3 template now ships a marker legend and marker-led example criteria, plus a new §3.1 **Status Discipline** defining all six markers and the evidence each one requires.
- `k79-conductor` Phase 3 marks criteria with the legend and requires the proof command on the `[DONE]` line; a rule no check can execute stays `[ASSERTED]`.
- `k79-verification-testing` §4 requires a passing test before `[DONE]`, allows `[ASSERTED]` for untestable wording, and bans `- [x]`.
- `specs/spec-status-markers.spec.md` records the contract, the anti-patterns, and the non-goals.

Markers: [OPEN] not started · [WIP] in progress · [DONE] verified with proof · [ASSERTED] wording only · [FAILED] · [BLOCKED].

#### Verification

- `node scripts/validate-skills.mjs` — 9 skills, frontmatter and references valid.
- `node scripts/sync-agents.mjs --check` — router block unchanged and in sync.
- `node scripts/release-notes.mjs --check` — entry schema and append-only history pass.
- `grep -rn "^- \[ \]\|^- \[x\]" skills/*/SKILL.md` — returns nothing.

#### Notes

No validator rule was added, so nothing enforces the markers; this is instruction text. The honest marker for that limitation is `[ASSERTED]`, which is exactly what the change introduces. Specs written before this entry are not retrofitted.

## Installation

```bash
bunx skills@latest add AbdulWadudh/k79-agent-skills -y
```

Default: project-local. Creates `.agents/skills/` and `skills-lock.json`; no agent selection and no per-agent mirrors. Advanced: add `-g` for `~/.agents/skills/`, or `-a <agent>` / `--agent '*'` for mirrors.

## Updating

Re-run the install command for the scope you use. `skills add` reads the latest default branch, so a separate update step is optional. For a hash-based refresh, run `bunx skills@latest update -y` (current scope) or `-g -y` / `-p -y`.
